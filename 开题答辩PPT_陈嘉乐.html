01 / 研究背景与意义

大模型能力很强，但“答案”不能只靠模型自己记住

01
知识更新滞后

模型知识停留在训练语料时间点，无法覆盖最新的规范、文档与企业内部资料。

02
领域知识不足

专业文档中的术语、编号与条文细节，通用模型往往掌握不准确。

03
幻觉与不可溯源

回答看似流畅却缺乏依据，用户无法判断结论来自哪一段原文。

解决方案 检索增强生成（RAG）：先检索外部知识，再让模型“看着材料回答”
用户提问自然语言问题
→
检索从知识库召回相关片段
→
增强补充上下文、精炼材料
→
生成大模型基于材料作答
→
溯源标注引用来源
研究意义

面向企业规章、技术文档、校园制度等私有资料，构建“上传即可问”的知识库问答系统，降低资料查找成本，使回答有据可查。

本课题定位

不训练模型，重点解决 RAG 链路中最关键的两个环节：检索是否准、上下文是否可用。

02 / 国内外研究现状

RAG 的三代范式：从“能检索”到“检索得好、用得好”

第一代
Naive RAG

检索 → 拼接 → 生成，流程直连。实现简单，但检索结果质量与上下文组织缺乏控制。

代表：Lewis 等（NeurIPS 2020）首次提出 RAG 框架

第二代
Advanced RAG

在检索前后增加优化：查询改写、混合检索、结果重排序、上下文压缩，显著提升相关性。

代表：RRF 融合、HNSW 向量索引、FLARE 主动检索

第三代
Modular RAG

把检索、增强、生成拆成可组合模块，按场景编排，支持多路召回与多轮迭代。

代表：模块化 RAG 综述（Gao 等，2023）

结论：RAG 的研究重心已从“能不能检索”，转向“检索得准不准、上下文用得好不好”。本课题正落在第二代向第三代过渡的关键环节上。

02 / 国内外研究现状

已有研究：应用落地多，检索与增强仍有空间

国外 · 基础方法

Lewis 等提出 RAG 框架，参数化与非参数化记忆结合，成为后续研究基础。

Gao 等系统梳理 RAG 三范式与评价方法。

Malkov 等提出 HNSW 图索引，成为向量检索主流结构。

Cormack 等提出 RRF 倒数排序融合，多路召回融合的经典方法。

Jiang 等提出 FLARE，由生成过程驱动主动检索。

国内 · 应用实践

王鑫林等综述 RAG 方法与应用；吴海周等研究知识库问答性能优化与参数调控。

高川等实现云端—本地双模式私有知识库问答，兼顾安全与效率。

张墨涵面向企业私有知识库实现检索增强问答。

张凯等基于混合 RAG 构建铁路工程规范问答。

马成业等提出查询反馈驱动的上下文蒸馏；马俊朋提出查询增强与上下文精炼方法。

02 / 不足与本课题切入点

三个待改进之处，对应本课题的三个设计动作

01
检索方式单一

纯向量检索对编号、缩写、专有名词的精确匹配较弱；纯关键词检索又抓不住同义表述。

→
混合检索

向量检索 + 关键词检索双路召回，对多路结果进行融合与重排序。

02
分块导致语义割裂

文档切片后脱离章节语境，片段单独看含义模糊，模型难以准确理解。

→
上下文增强

为片段补充文档级上下文，并结合查询改写与冗余过滤构建精炼上下文。

03
效果评价偏主观

多数系统只展示问答效果，缺少可复现的对比数据，难以说明设计是否有效。

→
可复现的对比实验

自建“问题—相关文档”评测样本，对比单一检索与混合检索、增强前后的效果。

03 / 研究目标与关键问题

做一套“上传即可问、回答可溯源”的知识库问答系统

研究目标
一个可运行、可演示、可评价的系统

· 支持多种格式文档上传、解析与入库，构建私有知识库

· 支持语义检索与关键词检索，并融合排序

· 支持上下文增强后的智能问答，回答标注来源

· 支持流式输出与多轮对话，响应满足实际使用

· 具备可复现的检索效果对比实验与测试报告

关键问题一
两种检索结果如何有效结合？

向量检索与关键词检索的排序尺度不同，不能简单拼接。需要确定融合方式、各路召回数量与重排序策略，并验证其相对单一检索的提升。

关键问题二
切分后的片段如何补齐语境？

片段脱离原文后语义不完整。需要确定上下文信息的来源与注入方式，并在“信息完整”与“上下文过长、噪声增多”之间取得平衡。

关键技术选择

· 向量表示：预训练嵌入模型，将文档片段与问题映射为向量

· 向量索引：近似近邻索引，支撑大规模片段的快速召回

· 词法索引：基于文本匹配的关键词检索，补足精确命中

· 融合与重排：对多路召回结果统一排序，可选重排序模型

· 生成与交互：大语言模型 + 流式输出 + 来源引用

验证方式

· 构建“问题—相关文档”评测样本，覆盖事实型与表述型问题

· 对比纯向量、纯关键词与混合检索的召回表现

· 对比上下文增强前后的问答相关性

· 记录首字响应时间与整体响应时间，评估可用性

· 说明：使用预训练模型，不涉及模型训练，无需标注训练集

05 / 重点设计一

混合检索：两路召回，一路排序

用户问题　→ 同时送入两路检索
向量检索

问题向量与片段向量计算相似度，擅长同义表述、语义相近的召回。

关键词检索

基于文本匹配，擅长编号、专有名词、缩写的精确命中。

Top-K 候选
Top-K 候选
融合排序（按排名统一合并，降低两路尺度差异）
可选重排序 → 输出最终上下文片段
为什么必须混合

例：问题中出现的“GB/T 编号”“第 5.2 条”这类内容，语义检索容易漂移；而“怎么申请”这类口语化表达，关键词又抓不住。两路结果互补，才能同时兼顾精确与语义。

设计要点

· 两路各取 Top-K，K 值可配置

· 融合按排名而非绝对分数，避免尺度不一致

· 支持切换纯向量 / 纯关键词 / 混合三种模式，便于对比

· 融合参数与 K 值通过评测样本调优

05 / 重点设计二

上下文增强：让片段“带着语境”进入模型

片段侧增强
为每个片段补充文档级上下文
增强前

“本条自发布之日起施行。”——脱离原文后无法判断指哪条、属于哪份文件。

增强后

“（《XX 管理办法》第三章 第 5.2 条）本条自发布之日起施行。”——检索与生成都能定位到语境。

上下文在向量化之前拼入片段，使检索阶段就能命中语境相关信息。

查询侧增强
改写与扩展用户问题
典型问题

口语化、省略、指代不明：“这个流程要多久？”

处理方式

结合会话上下文补全指代，生成多个检索式分别召回，再合并去重。

配合冗余过滤与长度控制，避免上下文过长导致关键信息被稀释。

05 / 数据设计

数据模型围绕“知识库—文档—片段—会话”展开

实体关键字段说明与关系
知识库编号、名称、描述、创建者文档的归属容器，一个知识库包含多份文档
文档编号、知识库编号、文件名、类型、状态与知识库多对一；记录解析进度与失败原因
文档片段编号、文档编号、序号、文本内容、上下文与文档一对多；保存增强后的上下文，支持回溯原文
向量片段编号、向量、维度与片段一一对应，写入向量索引供相似度检索
会话编号、用户、创建时间一次连续对话，支持多轮上下文继承
消息编号、会话编号、角色、内容、引用片段与会话一对多；记录引用来源，保证回答可追溯

设计关键：片段与原文的关联必须完整保留，使回答中的每一条引用都能定位到具体文档与位置；检索参数与融合配置单独存放，便于对比实验时切换。

05 / 重点难点与预期创新

难在“怎么证明它真的更好”

重点
融合策略与参数

两路召回数量、融合方式、是否重排序，都会影响最终排序结果，需要按评测结果逐步调整。

上下文的成本与效果

上下文越长信息越全，但噪声与耗时也随之增加，需要在完整性与效率之间取平衡。

难点
检索效果的量化评价

缺少公开的中文领域问答评测集，需要自行构造“问题—相关文档”样本，并保证样本覆盖不同类型提问。

多格式文档的解析质量

不同格式文档结构差异大，解析与分块策略不当会直接影响后续检索与问答效果。

预期创新点
① 检索互补

语义与词法双路召回，兼顾精确匹配与语义理解。

② 语境补齐

片段级上下文 + 查询侧改写，缓解分块语义割裂。

③ 可复现评价

自建评测样本，给出可对比的检索与问答效果数据。
